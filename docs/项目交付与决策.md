# 项目交付与无人值守决策记录

| 编号 | 需要拍板的事项 | 本轮决定 | 复盘依据与影响 |
|---|---|---|---|
| P-01 | 题库规模和分层 | 两场景各入库 12 题，练习 5、验证 2、考试 5；保持 bank-v1 的 frozen=false，直到正式成本与难度实测后再冻结 | 满足原计划结构，但不能假装正式题库已冻结。两种考试陷阱分别为提速 already-vectorized 止损题、表格 Bank Marketing 的 duration 泄漏诱饵。 |
| P-02 | 负 gap 和微弱 gap 怎么处理 | AutoGluon dev AUC 不高于 LightGBM 的 Spambase、Wine、EEG、QSAR 保留失败测量但不入正式 bank；Online Shoppers、Phishing 的极小正 gap 仅放练习，不做考试上限 | 不能为了凑数改写实测。Mushroom 的可见特征曾根据早期 dev 调整，也只放练习。 |

| P-04 | 无正式价格时如何联调 | TEST 价目和临时预算仅允许 dev manifest；脚本角色与已知参考候选仅用于链路测试，账本/看板/图表全部标明 TEST | 已用真实 macOS 沙箱、真实计时与 30 次 A 主循环任务跑通四线三遍 TEST 编排；24 道入库题的原始方案均在 dev 真实沙箱评分通过，逐题结果见 B-全题dev烟测.json；不证明模型自主研究或人民币/美元节省。 |

| P-06 | 正式验证与考试次数 | 同一 bank_version 各写全局一次性 attempt 标记；研究版必须先经过 3 遍配对验证准入，考试集只跑一轮 | 准入规则为每遍得分不低于默认版且平均成本更低。正式 run 需 Git HEAD 一致、工作区洁净、源文件哈希匹配，失败也不自动重试。 |
| P-07 | 朴素对照怎么实现 | 提供 config/naive.json：四角色使用同一通用提示词、全程 high、完整实验历史、不开能力库检索 | 实现“同一通用研究员”的可比对照；调用仍按 A 接口分阶段，不等于一个完全独立实现的单次大提示词 agent，正式报告应准确称谓。 |
| P-08 | 自研究成本怎么算 | 自动提案单独写 proposal_ledger/1，失败调用的可得 token 也计费；候选全部练习运行和所有提案费用一起进入研究总成本与回本点 | 不把提案成本伪装成某一道题的任务费用；TEST 回本仅为机制示意。选中设置/提示词文件用 SHA256 复核，再进入一次验证。 |
| P-09 | 自研究是否完全无预算 | 外层候选轮次不设金额硬上限；单次调用限制最多 8 个候选、输出上限 4096 token，内部每道 A 任务仍要求正预算并执行 90% 硬闸 | 这是对原“完全不设预算”的安全性折中。若比赛要求内部任务也无预算，需修改 A 调度与账本 schema 后重新验证，不能声称已实现。 |
| P-10 | 展示形式 | 保留可离线导出的单页看板，增加 localhost 每秒只读刷新与双运行分屏；四线图只从同批次、准入已通过的 12 份审计报告生成 | 无正式考试数据时不能制作正式得分图或录屏结论；现场演示结果不计入正式报告。 |
| P-11 | 自研究报告与考试配置如何对齐 | 出图时重审六份验证报告并重新计算准入，重验选中配置和提示词哈希，并核对验证及已准入考试的研究版 manifest 均指向该配置和 SHA256 | 防止改写准入字段，或把其他调参版本的考试成绩与某次自研究成本拼接成同一份正式报告。 |
| P-12 | 研究版未通过准入后怎样交付考试结果 | 跳过研究版考试，保留朴素版、默认空库、默认练过库三条线各三遍；报告明确拒绝原因和研究成本，不计算研究版回本点 | 一次性考试不会因为候选失败而丢失已跑结果，也不把未经准入的研究版画成正式第四条线。 |
| P-13 | 练习题上默认版胜出时选谁做验证 | 记录包含默认版的总胜者，但 selection 取最佳有效生成候选，让一次验证准入决定其去留；若全部提案无效，selection=null 并在验证前停下 | 避免把默认配置当作“研究版”制造虚假的第四条线，也保留真实候选未达标的负结果。 |
| P-14 | 未给定模型和题目预算时如何开展真实实验 | 选择可本地部署的 qwen3.5-27b，用两道 practice 题和自选 40,000 token 单题预算做 dev 试点；四桶各按 1 token 计量，价目明确 test_only=true、currency=TOKENS | 真正测试规划、执行、评分和记账；不能把 token 当现金，也不能把网关每日额度换算成 token。全部尝试见 真实模型试点.md。 |
| P-15 | 网关未落实结构化输出怎么办 | 在系统指令附完整角色 JSON Schema，客户端本地校验字段；兼容纯 JSON 围栏，拒绝其他杂文；每次原始可见输出留 dev 审计文件 | 原先规划者自造字段被静默当作空计划、总结者输出无效 JSON；现在可以区分格式错误与真正的无假设停止。 |
| P-16 | 预算预留如何避免无效运行状态 | 调用前检查账本已花费加 5,000 token 预留；拒发时关闭正在执行的节点并记 budget_cap | 实际单次调用可能超过预留和请求输出上限，不能宣称绝对硬封顶。两次表格运行分别在 36,998 和 35,550 token 停止；前者超过 90% 扩展阈值但低于 40,000 总预算。 |
| P-17 | 表格真实模型没有超过基线怎么办 | 保存负结果，不代填成绩；修正 15 个误写 Bank Marketing 的基线注释，诊断提示明确归一化 gap 分数可为负，另做低推理档 v2 对照 | Mushroom v1 两次实验、v2 三次实验均未超过基线；v2 耗费 35,550 token，不能作为模型自主提升的证据。 |
| P-18 | 真实模型中途返回坏 JSON 时怎么收尾 | 记 stop=error，保留此前接受的最佳节点并执行 C 的唯一一次 holdout；其他非模型代码异常仍抛错 | 跨运行经验复用试验已从旧库检索并引用 exp-0001，之后第 8 次规划坏 JSON；手工只执行 C 的封存/单次 holdout 补全，得到 25,455 token 的诚实报告，新增回归后未来可自动收尾。 |
| P-19 | 一次性报价怎样学习真实调用成本 | 批次中同一运行、同一场景的前序任务报告作为历史预测/实耗对，交给 C 已有的中位误差校准；不跨配置、重复轮次或场景混用 | German Credit 单题规划报价 1,900 token、实耗 35,106，暴露首题报价误差；校准只能改善后续报价，不能改变当前任务的预算闸门或抹去首题误差。 |
| P-20 | 模型总结生成非法经验时如何收尾 | 逐条拒绝证据节点或当前特征词无效的草稿，并将原草稿与原因写入任务审计；库版本冲突和冻结异常继续抛出 | 朴素 German Credit 在成功实验后因 `n0001` 被当作触发词而中断；已保留原 `stop=error` 和 campaign 失败记录，仅调用一次 C holdout 补全。此修复通过单元与真实沙箱端到端回归。 |
| P-21 | 四桶 token 预算被单次调用突破怎么办 | 将后续 dev 试点的请求前预留由 5,000 提高到 12,000 token，并保留 40,000 总预算、36,000 常规扩展阈值；旧运行及输入哈希不改 | 朴素 German Credit 第三轮最后一次修复从 34,645 花到 41,220，超出 1,220 token。网关实际推理用量可超过请求上限，12,000 是依据已观察最高单次 10,689 token 的审慎缓冲，不保证绝对不会超限；后续需量化预算遵守率。 |
| P-22 | 在无正式现金价格和题目预算时怎样实测自动自研究 | 复制两道 practice 题和配置到隔离项目，采用每题 40,000 四桶 token、12,000 请求预留；C 用 TEST 标记记录真实网关 token，先跑默认版三遍，再让模型提一轮受限候选并重复三遍 | 能测提案、版本化配置、练习任务、总研究花费和选择链路；TEST 单位数值等于报告 token 数，但不是现金，也不打开验证/考试题。原题库和正式价格表不动。 |
