# A 线实施决策记录

记录日期：2026-11-13。以下是无人值守实施时做出的可复盘决定，不修改《接口约定 v1》中的对外 schema。

| 编号 | 需要拍板的问题 | 本次决定 | 原因与复盘点 |
|---|---|---|---|
| A-01 | B/C 代码尚不存在，A 如何开发和验证 | A 通过文档约定的 harness 与 ledger 接口集成，测试使用注入的内存替身；生产运行缺少模块时清晰报错 | 保持分工边界，避免自行定义 B/C 的真实评分、价格或题目数据；明天检查 B/C 是否认可注入边界 |
| A-02 | 预算、模型、价格未知时是否填示例值 | 保持缺失并拒绝正式运行；hard_caps.json 使用已拍板的 90% 硬上限 | 不伪造财务数据；实际价格和预算到手后再填 |
| A-03 | 对外 schema 是否调整 | 不改 task/1、score/1、ledger/1、node/1、entry/1，内部实现允许增加不写入对外文件的状态 | 接口变更需要三人同意并升版本 |
| A-04 | 考试期能力库如何处理使用记录 | 冻结库只向账本记 library/use，不更新状态或版本 | 遵守考试冻结与可复现要求 |
| A-05 | 无法完成正式赛题评估时如何验收 A | 用假的 B/C 适配器跑完整主循环、预算闸门、节点接受、失败诊断、版本回放测试；正式成绩等待真实题包 | 测 A 的行为而不臆造比赛结果 |
| A-06 | 起点 n0000 的分数从哪里来 | 运行入口要求 B/C 提供一份真实的 dev score/1 基线结果，不由 A 读取隐藏的 bank.json，也不把未知值写成 0 | v1 的 TaskView 不公开基线分数，却要求 n0000 带基线分数；这是接口对接点，需 B/C 确认来源 |
| A-07 | 规划者预估如何利用历史效果修正 | 优先级先按预期增益/成本计算；历史经验用 3 个伪观察做收缩，规划误差倍率限定 0.5–1.5 | 文档规定修正方向但未给公式；限制小样本噪声主导，明天可用真实实验检查 |
| A-08 | 排队节点何时写入实验树 | 规划者的候选先留在 A 内存队列，选中时才落 node/1；每次选中都从当时最佳已接受节点分叉，复盘 switch/reallocate 会丢弃旧候选并重新规划 | 避免一开始排队的节点永远指向旧父节点；未执行的建议不作为实验节点，意外退出后候选需重新规划 |
| A-09 | Responses API 的 token 如何交给 C 记价 | 把包含关系拆成互斥的输入、缓存输入、可见输出、推理输出四桶，再调用 Ledger.llm_call | 防止 cached/reasoning 与总输入/输出重复计费；C 的价格表需按这四桶填写 |
| A-10 | 考试期总结经验怎样保留 | 仍调用一次总结者，把草稿追加到任务目录 experience_drafts.jsonl，并记 library/freeze 事件，不改冻结库 | 兼顾“考试只读”和“经验只记日志”；此内部文件不是能力库的状态或版本 |
| A-11 | 异常分数何时叫诊断者 | B 返回作弊标记、分数 > 1.2、或比父节点低 0.5 以上时触发；异常高分即使达到 ceiling 也先诊断 | 文档没给数值门槛；这是保守的初版启发式，正式赛题可校准，节点接受仍严格按 v1 评审规则 |
| A-12 | 停止与收尾顺序 | 到时间上限或总预算已耗尽时不再叫总结者；其他停止先总结，最后写 stop 事件，令 stop 后花费不再变化 | 保留 90% 预算闸门余下的收尾空间，避免账本显示已停止却继续调用模型 |
| A-13 | 赛题正式数字的时间 | 采用 M3 练习集切分预演、M4 冻结代码和能力库后只跑一次正式考试的顺序 | 同时满足“尽早拿预演数字”与“考试集不回头重跑”；明天全队复核 |
| A-14 | 报价事件由谁写 | A 在首个实验前保存 opening_plan.json，并提供 on_initial_plan 回调；报价及误差修正仍交 C 的报价模块写 ledger/1 quote | 保持 v1 的 C 责任边界；C 可以在回调里先报价再放行实验，CLI 单独运行时只留预测文件而不伪造报价事件 |
| A-15 | 回放如何防止文件或设置事后漂移 | CLI 成功结束后写 A 内部的 replay_context.json，封存 manifest、基线、配置、价格、硬上限、触发词、提示词、实验树、代码、分数与历史库快照的 SHA256；正式回放先核对再重评分 | 不改 B/C 的 v1 schema；哈希能发现事后变动，但不是数字签名，也不能重现模型的随机生成过程；中途失败的运行不会有完整封存 |
| A-16 | 可调设置与库规则怎样保持一致 | CLI 只接受 manifest 已哈希记录的配置和模型；自研究时用同一份 agent.json 驱动角色、调度和能力库规则，覆盖不可信的继承环境变量 | 避免角色用了新设置、经验库仍用默认阈值，或回放与运行所用模型不一致 |
| A-17 | 一条经验/改窄操作的证据怎样追踪 | 总结者每条草稿带 node_ids；A 逐条核对本任务节点后写入。改窄只接受已引用且失败的条目，且新条件保留旧条件、附失败节点证据 | 避免把整道题所有节点笼统地当作每条经验的证据；无证据的草稿丢弃 |
| A-18 | 真实闭环何时算跑通 | 目前只认本地 A 与 B/C 假适配器的测试通过；待 B/C 真实模块、模型价格、预算、题包和基线到位后再跑 M1 集成及正式数字 | 不把模拟分数或零价格写成比赛结果；明天需安排对接验收 |
| A-19 | 原目录没有版本控制，manifest 的 code_commit 如何填 | 在现有项目目录初始化本地 Git，仅提交代码、配置、文档和测试；聊天归档与运行产物留在本地但忽略提交 | 给 C 后续 manifest 提供可追溯的代码提交号；没有配置远端或上传任何内容 |
