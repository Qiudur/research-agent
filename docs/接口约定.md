2026-11-13 定稿。四份约定，外加一份附录（M4 要用的可调设置）。

任何改动须三人同意，并把对应的 schema 版本号加一，比如 `task/1` 改成 `task/2`。

| 约定 | 谁负责 | 谁用 |
|---|---|---|
| 1. 任务包格式 | B | A、C |

## 0. 通用约定

- **Python 3.11 及以上**（本机是 3.13）。
- **文件格式**：一律 UTF-8。结构化数据用 JSON，只追加的记录用 JSONL（一行一条）。
- **schema 字段**：每个 JSON 文件、每条 JSONL 记录都带 `schema`，写成「名字/版本」，如 `"node/1"`。读的一方遇到不认识的版本直接报错，不猜。
- **时间**：ISO 8601 UTC，精确到毫秒，如 `"2026-11-13T14:15:00.123Z"`。时长一律用秒，浮点数。
- **钱**：浮点数。币种由价格表的 `currency` 决定，全系统只用这一个币种。
- **两套「验证」别混**：
  - **练习 / 验证 / 考试**：题的分层，记在 `bank.json`。
  - **dev / holdout**：一道题内部的数据切分。dev 给评审脚本判断「这次改进算不算数」；holdout 只在任务结束时打一次最终分，agent 全程碰不到。

### 编号格式

| 东西 | 格式 | 例子 |
|---|---|---|
| 任务 | `<场景前缀>-<短名>`，前缀 `tab`（表格）或 `spd`（提速） | `tab-titanic`、`spd-rolling-max` |
| 一次运行 | `run-<日期>-<时分秒>-<4 位随机>` | `run-20261113-221500-a3f9` |
| 节点 | `n` + 4 位序号，在「一次运行的一个任务」内唯一 | `n0007` |
| 经验 / 技能 / 工具 | `exp-` / `skl-` / `tool-` + 4 位序号 | `exp-0042` |
| 能力库版本 | `lib-` + 序号，每变化一次加一，空库是 `lib-0` | `lib-37` |
| 题库版本 | `bank-v` + 序号 | `bank-v1` |

### 目录结构

```
tasks/                        ← B 负责
  bank.json                   ← 题库版本；每道题属于哪一层、难度、是不是埋坑题
  <task_id>/
    task.json                 ← 给 agent 看的任务说明
    workspace/                ← agent 能看到的：训练数据或原始代码、画像 profile.json
    hidden/                   ← agent 看不到：dev 和 holdout 数据、参考最优解、随机输入生成器
config/
  prices.json                 ← 价格表（C 负责）
  hard_caps.json              ← 硬上限（只有人能改）
  agent.json                  ← 可调设置（A 负责，见附录）
  prompts/<role>.md           ← 各角色提示词（A 负责）
  triggers.json               ← 触发特征词表（A、B 共同维护）
runs/<run_id>/                ← 一次运行 = 一种配置 × 一遍 × 一个阶段
  manifest.json               ← C 负责
  ledger.jsonl                ← 运行级事件
  library/                    ← 这次运行自己的能力库（练习阶段从空库起步）
  tasks/<task_id>/
    ledger.jsonl              ← 这个任务的账本
    tree.jsonl                ← 实验树
    nodes/<node_id>/          ← 每个实验一个目录
```

每个任务一份账本，是因为考试阶段表格题会并行跑，多个进程往同一个文件追加，容易互相截断。

### 触发特征词表 `config/triggers.json`

B 的画像脚本输出的特征、能力库条目的触发特征，都只能用这张表里的词。加词要 A、B 都同意。

```json
{
  "schema": "triggers/1",
  "tabular": ["high_cardinality_categorical", "missing_heavy", "class_imbalance", "small_sample", "many_numeric", "datetime_column", "id_like_column", "possible_leakage"],
  "speedup": ["nested_python_loop", "rowwise_pandas_apply", "repeated_recompute_window", "list_membership_in_loop", "string_concat_in_loop", "recursion_no_memo", "already_vectorized"]
}
```

## 1. 任务包格式（B 负责；A、C 使用）

### 1.1 `tasks/<task_id>/task.json`

只放 agent 可以看的内容。题属于哪一层、难度、是不是埋坑题、基线和上限的原始分，都放在 `bank.json`，A 加载任务时拿不到。

表格题：

```json
{
  "schema": "task/1",
  "task_id": "tab-titanic",
  "scenario": "tabular",
  "title": "Titanic 乘客生存预测",
  "description": "给 agent 看的任务说明，Markdown。",
  "metric": {"name": "auc", "higher_is_better": true},
  "deliverable": {
    "file": "solution.py",
    "function": "fit_predict",
    "signature": "fit_predict(train: pd.DataFrame, test: pd.DataFrame, target: str) -> np.ndarray",
    "returns": "test 每一行属于正类的概率，长度等于 len(test)"
  },
  "budget": {"money": null, "wall_seconds": 1800},
  "limits": {"run_seconds": 300, "memory_mb": 4096}
}
```

提速题只有这几处不同：

```json
{
  "scenario": "speedup",
  "metric": {"name": "speedup", "higher_is_better": true},
  "deliverable": {
    "file": "solution.py",
    "function": "max_drawdown",
    "signature": "与 workspace/original.py 里的同名函数完全一致",
    "returns": "与 original.py 的结果一致；浮点数允许 1e-9 的相对误差"
  }
}
```

- `budget.money` 拿到价格表后再填，填之前是 `null`，A 的调度器遇到 `null` 直接报错。
- 预算闸门的 90% 硬上限不在这里，在 `config/hard_caps.json`。

### 1.2 `workspace/`

- **表格题**：`train.csv`（只有训练部分，带目标列）、`profile.json`。
- **提速题**：`original.py`、`example.py`（演示怎么调用、典型输入规模）、`profile.json`。

`profile.json` 由 B 的画像脚本预先生成：

```json
{
  "schema": "profile/1",
  "features": ["high_cardinality_categorical", "missing_heavy"],
  "summary": {"rows": 891, "columns": 11, "target_rate": 0.38, "columns_detail": []}
}
```

提速题的 `summary` 放热点函数和各段耗时。`features` 只能用触发特征词表里的词。

### 1.3 `tasks/bank.json`

```json
{
  "schema": "bank/1",
  "version": "bank-v1",
  "frozen": true,
  "tasks": [
    {
      "task_id": "tab-titanic",
      "tier": "practice",
      "difficulty": "medium",
      "trap": null,
      "score_formula": "gap",
      "baseline_raw": 0.823,
      "ceiling_raw": 0.851,
      "naive_cost": 0.42
    }
  ]
}
```

- `tier`：`practice` / `validation` / `exam`。
- `difficulty`：用朴素版实际跑的花费定档，`easy` / `medium` / `hard`，实测前是 `null`。
- `trap`：`null` / `leakage` / `cheat_bait` / `stop_loss`。
- `score_formula`：`gap` 表示（原始分 − 基线）÷（上限 − 基线），表格题用；`ratio` 表示加速比 ÷ 参考最优解的加速比，提速题用。
- `frozen` 为 `true` 以后，这个版本不再改；加题只进下一个版本。

### 1.4 Python 接口（B 提供，模块名 `harness`）

```python
from harness import load_task, list_tasks, run_script, score, profile_code

load_task(task_id: str) -> TaskView
list_tasks(bank_version: str, tier: str | None = None, scenario: str | None = None) -> list[str]
run_script(task_id: str, node_dir: Path, argv: list[str], limits: Limits | None = None) -> RunResult
score(task_id: str, node_dir: Path, split: Literal["dev", "holdout"], seed: int | None = None) -> ScoreResult
profile_code(task_id: str, node_dir: Path) -> dict   # 提速题：对 agent 的新代码做性能画像
```

- `TaskView`：`task.json` 的全部字段，加上 `workspace: Path` 和 `features: list[str]`。
- `run_script`：给执行者跑探索性脚本用，比如做数据分析。在沙箱里运行：`workspace/` 只读，`node_dir` 可写，不能联网，`hidden/` 不挂进去。
- `Limits`：`run_seconds`、`memory_mb`，默认取 `task.json` 的 `limits`。
- `RunResult`：

```json
{"exit_code": 0, "timed_out": false, "oom": false, "seconds": 12.3, "peak_mb": 812, "stdout_tail": "", "stderr_tail": ""}
```

`stdout_tail` 和 `stderr_tail` 各保留最后 4 KB。

### 1.5 `ScoreResult`

```json
{
  "schema": "score/1",
  "ok": true,
  "split": "dev",
  "score": 0.62,
  "raw": 0.8405,
  "spread": 0.004,
  "correct": true,
  "cheat_flags": [],
  "error": null,
  "seconds": {"run": 12.3, "queue": 4.1},
  "seed": 1234
}
```

| 字段 | 含义 |
|---|---|
| `score` | 归一化分数，按 `score_formula` 算。可以小于 0，也可以大于 1；大于等于 1 就是「分数到顶」 |
| `raw` | 原始指标：表格题是 AUC 等，提速题是加速比 |
| `spread` | 正常波动。表格题：三个随机种子下归一化分数的总体标准差（score 为中位数）；提速题：N 次计时的四分位距 ÷ 中位数 × 加速比 |
| `correct` | 提速题正确性检查是否通过；表格题三次预测均合法且无作弊时为 `true`。不通过时 `score` 为 0 |
| `cheat_flags` | 命中的防作弊检查，见下表。非空时这个节点一律不接受 |
| `error` | 跑不起来时填 `{"kind": ..., "message": ..., "trace_tail": ...}`，`kind` 取 `timeout` / `oom` / `exception` / `bad_output`，同时 `ok` 为 `false`、`score` 为 `null` |
| `seconds.queue` | 提速题排队等测速的时间 |

防作弊标记：

| 标记 | 场景 | 含义 |
|---|---|---|
| `reads_hidden` | 都有 | 试图读 `hidden/` 或别的题的文件 |
| `writes_outside_node` | 都有 | 往自己的节点目录以外写文件 |
| `network` | 都有 | 试图联网 |
| `dev_in_train` | 表格 | 训练数据里混进了 dev 的行（按行哈希检查） |
| `output_cache` | 提速 | 换新随机种子后结果对不上，像是提前存了答案 |
| `behavior_change` | 提速 | 边界输入上和原函数结果不一致 |

规则：

- **holdout 只能由评估流程调用**：调用时必须设置环境变量 `RA_EVAL=1`。这个变量由 C 的编排脚本设置，agent 的进程里没有，在 agent 进程里调用会直接报错。
- **提速题测速要排队**：`score()` 会先拿一把全机唯一的测速锁 `runs/.timing.lock`，排队时间记进 `seconds.queue`。
- **测速方法**：先预热一次；原代码和新代码交替测 N 次（dev 默认 7 次，holdout 默认 15 次），取中位数。
- **正确性检查**：每次调用都用新的随机种子生成输入，种子记在 `seed` 里，方便重跑。

## 2. 账本格式（C 负责，含写入模块；A 调写入模块记账，C 读）

### 2.1 `runs/<run_id>/manifest.json`

一次运行开始时由 C 的编排脚本写入。

```json
{
  "schema": "run/1",
  "run_id": "run-20261113-221500-a3f9",
  "phase": "practice",
  "config": "default_lib",
  "rep": 1,
  "bank_version": "bank-v1",
  "tasks": ["tab-titanic", "tab-adult"],
  "library": {"root": "runs/run-20261113-221500-a3f9/library", "start_version": "lib-0", "frozen": false},
  "agent_config": {"path": "config/agent.json", "sha256": "..."},
  "prices": {"path": "config/prices.json", "sha256": "..."},
  "hard_caps": {"budget_ratio": 0.9},
  "code_commit": "git 提交号",
  "model": "开赛给的模型名",
  "started_ts": "2026-11-13T14:15:00.123Z",
  "ended_ts": null
}
```

- `phase`：`dev`（开发调试）/ `practice` / `validation` / `exam` / `self_research` / `demo`。
- `config`：`naive`（朴素版）/ `default`（默认设置、空能力库）/ `default_lib`（默认设置 + 练好的能力库）/ `tuned_lib`（研究出来的版本 + 练好的能力库），对应主图的 4 条线。
- `rep`：第几遍，1–3。
- `tasks`：按执行顺序排列。练习阶段的顺序固定。
- `library`：考试阶段指向对应练习运行的能力库，`frozen` 为 `true`。

### 2.2 事件公共字段

每条事件都带：

```json
{"schema": "ledger/1", "seq": 17, "ts": "2026-11-13T14:15:03.456Z", "run_id": "run-20261113-221500-a3f9", "task_id": "tab-titanic", "node_id": "n0007", "kind": "llm_call"}
```

`seq` 在每个账本文件内从 1 开始递增。运行级事件的 `task_id` 为 `null`；和具体节点无关的事件，`node_id` 为 `null`。

### 2.3 事件种类

| `kind` | 谁触发 | 额外字段 |
|---|---|---|
| `task_start` | A | `budget`（钱）、`wall_seconds` |
| `quote` | C 的报价模块 | `predicted: {cost, seconds, score}`、`basis`（依据：规划者的预估，以及用了哪段历史误差修正） |
| `llm_call` | A，经写入模块 | `role`、`purpose`、`effort`、`model`、`tokens: {input, cached_input, output, reasoning}`、`cost`、`seconds`、`prompt_hash`、`ok`、`error` |
| `experiment` | A，转记 B 的运行结果 | `attempt`（1–3）、`seconds_run`、`exit_code`、`timed_out`、`oom` |
| `score` | A，转记 B 的评分结果 | `split`、`score`、`raw`、`spread`、`correct`、`cheat_flags`、`seconds_queue` |
| `review` | A | `trigger`（`plateau` / `behind_schedule`）、`decision`（`continue` / `switch` / `reallocate` / `stop`）、`budget_moves: [{from, to, amount}]`、`note` |
| `library` | A | `op`（`query` / `use` / `write` / `narrow` / `promote` / `demote` / `retire` / `freeze`）、`entry_ids`、`version_after` |
| `stop` | A | `reason`（`budget_cap` / `time` / `ceiling` / `planner` / `stop_loss` / `error`；`stop_loss` 只在配置了 `stop_loss` 开关时出现）、`best_node`、`dev_score` |
| `task_end` | C 的编排脚本 | `holdout_score`、`best_node`、`total_cost`、`seconds: {llm, run, queue, wall}`、`quote_error: {cost, seconds, score}` |
| `run_start` / `run_end` | C 的编排脚本 | 写在运行级账本里，`run_end` 带 `total_cost` |

枚举值：

- `role`：`planner` / `executor` / `diagnoser` / `summarizer`。评审是脚本，没有这个角色。
- `purpose`：`plan`（列假设）/ `quote`（报价时的预估）/ `code`（写代码）/ `fix`（修 bug）/ `diagnose` / `review`（复盘）/ `summarize`（写经验）。
- `effort`：`low` / `medium` / `high`。

耗时三块：`llm_call.seconds` 是等模型，`experiment.seconds_run` 是跑实验，`score.seconds_queue` 是排队测速。

### 2.4 写入模块（C 提供，模块名 `ledger`）

```python
from ledger import Ledger, Usage

lg = Ledger.open(run_dir: Path, task_id: str | None)
lg.llm_call(*, node_id: str | None, role: str, purpose: str, effort: str, model: str,
            usage: Usage, seconds: float, prompt_hash: str, ok: bool = True, error: str | None = None) -> float
            # 按价格表算钱、写一条 llm_call，返回这次花的钱
lg.emit(kind: str, *, node_id: str | None = None, **fields) -> None
lg.spent() -> float          # 这个任务到现在一共花了多少钱，预算闸门用
lg.elapsed() -> dict         # {"llm": ..., "run": ..., "queue": ..., "wall": ...}

Usage(input: int, cached_input: int = 0, output: int = 0, reasoning: int = 0)
```

- 价格表里找不到这个模型、或者价格还是 `null`，就直接报错，绝不记成 0 元。
- M0 当天 C 先交一个同样签名的最简版本（只写文件，不算钱）。A 先用它，C 之后替换成完整版，A 的代码不用改。

### 2.5 `config/prices.json`

```json
{

  "currency": "CNY",
  "unit_tokens": 1000000,
  "models": {
```

## 3. 实验树节点格式（A 负责；C 使用）

### 3.1 `runs/<run_id>/tasks/<task_id>/tree.jsonl`

每当一个节点有变化，就追加一行它的**完整快照**。同一个 `node_id` 以最后一行为准，读的一方按 `node_id` 取最后一行。

```json
{
  "schema": "node/1",
  "run_id": "run-20261113-221500-a3f9",
  "task_id": "tab-titanic",
  "node_id": "n0007",
  "parent": "n0003",
  "created_ts": "2026-11-13T14:20:00.000Z",
  "updated_ts": "2026-11-13T14:21:30.000Z",
  "hypothesis": "对类别数很多的列做目标编码",
  "rationale": "画像显示有 3 列类别数超过 100",
  "origin": "plan",
  "cites": ["exp-0042", "skl-0003"],
  "estimate": {"gain": 0.05, "cost": 0.12, "seconds": 90},
  "priority": 0.41,
  "status": "accepted",
  "attempts": 2,
  "failure": null,
  "score": {"dev": 0.62, "raw": 0.8405, "spread": 0.004, "correct": true, "cheat_flags": []},
  "cost": 0.083,
  "seconds": {"llm": 41.2, "run": 12.3, "queue": 0.0},
  "library_version": "lib-37",
  "calls": [{"role": "executor", "effort": "low", "n": 3}],
  "code_dir": "nodes/n0007"
}
```

| 字段 | 说明 |
|---|---|
| `parent` | 从哪个节点改出来的；起点节点为 `null` |
| `origin` | `root`（起点）/ `plan`（正常排队）/ `explore`（每 4 个节点留给其他方向的名额）/ `diagnose`（诊断者改出来的）/ `draft`（从零起草） |
| `cites` | 提这个假设时用了能力库里哪些条目。能力库靠它给条目加分减分 |
| `estimate` | 规划者的预估：提升多少（归一化分数）、花多少钱、多少秒。报价和预估误差曲线都用它 |
| `priority` | 排队用的优先级：预期提升 ÷ 预估花费，再用经验库的历史效果和规划者过去的预估误差修正 |
| `status` | 见下面的状态流转 |
| `attempts` | 一共尝试了几次，包括执行者自己修 bug，最多 3 |
| `failure` | 失败时填 `{"kind": ..., "summary": ...}`，`summary` 是一句话原因 |
| `score.dev` | dev 上的归一化分数。holdout 分数不写在节点里，只写在 `task_end` 事件里 |
| `library_version` | 建这个节点时能力库的版本号。重跑时按它切回去 |

### 3.2 状态流转

```
queued → running → succeeded → accepted
                             → rejected
                 → failed（修了 3 次还跑不通）
```

- **起点节点 `n0000`**：表格题是基线方案（默认参数的 LightGBM），提速题是原始代码。它的分数就是基线，状态直接是 `accepted`。
- **接受规则**（评审脚本执行）：节点 `succeeded`，`cheat_flags` 为空，而且它的 dev 分数比当前最好的已接受节点高出 `max(自己的 spread, 最好节点的 spread)` 以上，才是 `accepted`；否则是 `rejected`。

### 3.3 `nodes/<node_id>/`

| 文件 | 内容 |
|---|---|
| `solution.py` | 交付物 |
| 其他文件 | agent 自己写的辅助脚本 |
| `run.log` | 每次尝试的输出，按尝试次数分段 |
| `score.json` | `ScoreResult` 原样存下 |
| `parent.diff` | 和父节点代码的差异 |

## 4. 能力库接口（A 负责；B 的技能层和工具库、C 的看板使用）

### 4.1 存储：`runs/<run_id>/library/`

```
library/
  state.json                    ← 当前版本的全部条目，每次变化后整体重写
  changelog.jsonl               ← 每次变化一行，只追加
  snapshots/lib-37.json         ← 每个版本一份快照，重跑时按版本号加载
  skills/skl-0003.md            ← 技能全文
  tools/tool-0002.py            ← 工具代码
  tools/tool-0002.cases.jsonl   ← 工具的回归测试用例
```

### 4.2 条目 `Entry`

```json
{
  "schema": "entry/1",
  "id": "exp-0042",
  "kind": "experience",
  "scope": "domain",
  "scenario": "tabular",
  "triggers": ["high_cardinality_categorical"],
  "conditions": "类别数超过 100，且样本量超过 1 万",
  "action": "对这些列做 5 折目标编码",
  "negative": false,
  "effect": {"uses": 5, "wins": 4, "mean_gain": 0.03, "mean_cost": 0.10},
  "credibility": 0.72,
  "status": "active",
  "sources": [{"run_id": "run-20261113-221500-a3f9", "task_id": "tab-adult", "node_ids": ["n0007"]}],
  "created_version": "lib-12",
  "updated_version": "lib-37"
}
```

| 字段 | 说明 |
|---|---|
| `kind` | `experience` / `skill` / `tool` |
| `scope` | `domain`（题目经验）/ `method`（方法经验） |
| `scenario` | `tabular` / `speedup` / `any` |
| `triggers` | 只能用触发特征词表里的词。查找时拿它和任务画像的 `features` 匹配 |
| `conditions` | 适用条件，可以改窄 |
| `negative` | `true` 表示「这招没用、白花钱」，提醒规划者别再试 |
| `status` | `active` / `demoted` / `retired` |

技能额外有 `summary`（一句话简介，平时放进提示词的就是它）和 `body_path`（全文路径）。工具额外有 `module`、`function`、`cases_path`、`from_skill`。

### 4.3 变更记录 `changelog.jsonl`

```json
{
  "schema": "libchange/1",
  "version": "lib-38",
  "ts": "2026-11-13T15:02:11.000Z",
  "op": "narrow",
  "entry_id": "exp-0042",
  "before": {"conditions": "类别数超过 100"},
  "after": {"conditions": "类别数超过 100，且样本量超过 1 万"},
  "reason": "在两道样本量不到 1 万的题上失灵",
  "evidence": [{"run_id": "run-20261113-221500-a3f9", "task_id": "tab-titanic", "node_ids": ["n0011"]}],
  "actor": "online"

```

- `op`：`write` / `update` / `narrow` / `promote` / `demote` / `retire` / `merge`。
- `actor`：`online`（随做随改）/ `self_research`（研究自己时的大改）/ `human`。
- C 的「能力库进化史」直接读这个文件。

### 4.4 Python 接口

**高层，A 实现，A 的规划者、总结者调用：**

```python
from library import Library, LibraryFrozen

lib = Library.open(root: Path, version: str | None = None, frozen: bool = False)
      # version=None 打开最新版本；指定版本则只读，重跑用
lib.version -> str
lib.query(scenario: str, features: list[str], k: int = 8,
          kinds: tuple = ("experience", "skill")) -> list[Entry]
lib.brief(entries: list[Entry]) -> str          # 放进提示词的短文本：技能只给名字和一句话简介
lib.load_skill(skill_id: str) -> str            # 规划者选中某个技能后，加载它的全文
lib.record_use(entry_id: str, *, run_id: str, task_id: str, node_id: str,
               accepted: bool, gain: float, cost: float) -> None   # 更新可信度和效果统计
lib.write_experiences(drafts: list[dict], *, source: dict) -> list[str]   # 总结者的产出入库，返回新编号
lib.narrow(entry_id: str, conditions: str, *, reason: str, evidence: list) -> None
lib.changelog(since: str | None = None) -> list[dict]
```

**底层写入，A 实现，B 的技能层和工具库用：**

```python
lib.get(entry_id: str) -> Entry
lib.put(entry: Entry, *, op: str, reason: str, evidence: list, actor: str) -> str   # 返回新版本号
```

所有写操作，包括高层的那几个，最后都走 `put`。这样版本号、变更记录、快照、冻结检查只在一个地方实现，谁也绕不过去。

**技能层和工具库，B 实现（技能层 M4，工具库 M5）：**

```python
from library.skills import promote_candidates, promote_to_skill, demote_skill
from library.tools import promote_to_tool, run_cases

promote_candidates(lib: Library) -> list[list[str]]                          # 哪些经验够格升级成技能
promote_to_skill(lib: Library, exp_ids: list[str], body: str, summary: str) -> str   # 返回技能编号
demote_skill(lib: Library, skill_id: str, *, reason: str, evidence: list) -> None
promote_to_tool(lib: Library, skill_id: str, code: str, cases: list[dict]) -> str    # 先跑全部用例，过了才入库
run_cases(lib: Library, tool_id: str, code: str | None = None) -> dict       # 新版本必须通过全部旧用例才能替换
```

**冻结**：`frozen=True` 时，任何写操作都抛 `LibraryFrozen`。考试阶段 `record_use` 只往账本里记一条 `library` 事件，不改能力库。

### 4.5 默认规则

这些数都写在 `config/agent.json` 的 `library_rules` 里，「研究自己」可以调。

| 规则 | 默认值 |
|---|---|
| 新条目的可信度 | 0.5 |
| 用了之后节点被接受 | 可信度 +0.1 |
| 用了之后节点没被接受 | 可信度 −0.15，结果夹在 0 到 1 之间 |
| 不再推荐 | 可信度低于 0.3（状态改为 `demoted`） |
| 淘汰 | 已经是 `demoted`，又连续 3 次无效 |
| 经验升级成技能 | 可信度不低于 0.7，并且在至少 2 道不同的题上有效 |
| 技能升级成工具 | 同一段代码在至少 2 道题上原样有效，并且通过全部回归用例 |
| 条数上限 | 经验 200 条、技能 30 个、工具 30 个；超了先淘汰可信度最低的 |

## 附录：可调设置 `config/agent.json`（A 负责；B 的「研究自己」改它）

```json
{
  "schema": "agent/1",
  "effort": {"planner": "high", "executor": "low", "diagnoser": "high", "summarizer": "medium"},
  "max_attempts": 3,
  "plateau_nodes": 5,
  "behind_schedule": {"spent_ratio": 0.5, "progress_ratio": 0.5},
  "explore_every": 4,
  "query_k": 8,
  "prompts": {
    "planner": "config/prompts/planner.md",
    "executor": "config/prompts/executor.md",
    "diagnoser": "config/prompts/diagnoser.md",
    "summarizer": "config/prompts/summarizer.md"
  },
  "library_rules": {
    "init_credibility": 0.5, "win_delta": 0.1, "loss_delta": -0.15,
    "demote_below": 0.3, "retire_after_losses": 3,
    "skill_min_credibility": 0.7, "skill_min_tasks": 2, "tool_min_tasks": 2,
    "max_experiences": 200, "max_skills": 30, "max_tools": 30
  }
}
```

**可选开关**（A 负责）：下面这些键默认不出现在 `config/agent.json` 里；键缺省或为 `null` 就是原来的行为。类型或范围不对会在 `Scheduler` / `RoleAgents` 构造时直接报错。

| 键 | 取值 | 作用 |
|---|---|---|
| `stop_loss` | `{"spd": {...}, "tab": {...}}`，每项含 `first_n_no_gain`、`consecutive_no_gain`（整数 1–100，可只写一个） | 场景由 task_id 前缀（`spd-` / `tab-`）判断。前 N 个完成的非根节点都没被接受，或连续 K 个完成节点没被接受（接受、拒绝、失败的节点都算完成），就以 `stop_loss` 停止，不管计划里还剩几条假设；预算和时间硬上限同时成立时仍记 `budget_cap` / `time`；停止后照常调用总结者。触发时刚完成的那个节点不再叫诊断者。 |
| `ceiling_excludes_baseline` | `true` / `false` | 为 `true` 时，最佳节点仍是 `n0000` 就不因分数 ≥ 1 判 `ceiling`，规划者照常开局；只有被接受的非根节点达到 1 才判到顶。 |
| `planner_mode` | `"standard"`（默认）/ `"lean"` | `lean` 时规划者输出 schema 不再要求 `budget_allocation`（可省略或给空数组，给了仍会校验），规划和复盘的输入里也不再带 `allocations`；配合 `config/prompts/planner_lean.md`（在 `prompts.planner` 里指定）。 |
| `hypotheses_per_plan` | 整数 1–20 | 写进规划者调用的输入状态，提示词据此要求一次给出这么多条假设。 |
| `failure_feedback` | `true` / `false` | 为 `true` 时执行者修复调用和诊断者调用的输入里多一个 `last_failure`：`phase`（`executor` / `run` / `score`）、`category`（`exception` / `timeout` / `oom` / `score`）、`cheat_flags`、`correct`、`stderr_tail`（运行 stderr 末尾，至多 600 字符，含 hidden 等任务私有路径的行会被删掉）；诊断者的 `advice` 也会拼进它生成的新假设的 `rationale`。配合 `config/prompts/executor_lean.md`。 |
| `cost_priors` | `{"spd": 2500, "tab": 8000}`（正数） | 调度器算优先级和判断「放得下」时，用这个固定值代替规划者给的单条假设花费估计；节点里记录的 `estimate` 仍是规划者原值。 |

- 「研究自己」能改的：这个文件、`config/prompts/` 里的提示词、能力库里的技能和工具。
- 不能改的：`config/hard_caps.json`、价格表、题库、评分器。
- 「研究自己」的任务包（B 做）：工作区是上面这些可改内容的一份副本；交付物是改过的副本；评分器用这份副本跑一组练习题，按「每花 1 元拿多少分」打分。
