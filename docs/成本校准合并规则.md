# 朴素成本校准的合并规则

决策日期：2026-11-14。此规则在 24 题校准完成前固定；制定时提速组已开始运行，早期结果和一次无效 JSON 停止均保留。它定义内部 dev 的资源成本与难度，不代表比赛现金价格或正式考试成绩。

## 协议

- 模型为可本地部署的 qwen3.5-27b，经授权网关调用；朴素配置统一高推理、完整历史、无能力库检索。每题三次独立运行、空库起步，每次自定预算 40,000 个四桶合计 token，请求前预留 12,000、请求输出上限 2,048 token；允许同题三遍最多三路并发，评分在单一进程内串行。
- 仅复制题包可见工作区和 dev 评分所需数据，不复制表格 holdout.csv，也不调用 holdout。提速与表格各 12 题可在隔离机器上分组运行；跨机器的速度分数不得直接合并，token 成本仍需对齐代码提交、模型、配置和题包 SHA。
- 每次尝试保留 protocol、manifest、四桶账本、停止原因、错误、输入哈希和运行目录。模型提前停止或网关失败也是结果，不删除、不覆盖；重试必须新建 campaign 并注明原因。

## 合并与判定

1. 先核对每题三次尝试的代码、模型、题包和价格单位一致，四桶 token 与账本一致，且没有 holdout 尝试。token 消耗缺失的任务暂不入库。
2. 将正常完成 A 主循环、账本完整且实际消耗不超过单题预算的尝试计为完成；无效 JSON 等提前错误仍计入实际 token 消耗。若三次中少于两次完成，该题先列为待复测，题库不因此冻结。
3. 对至少两次完成的任务，朴素成本定义为三次尝试 token 总和除以完成次数。这是含失败开销的观察每次完成成本，故不会把便宜的失败误判为容易；同时原样报告完成率、三次成本区间和 dev 分数，不把该成本说成现金。
4. 两个场景分别按上述朴素成本从低到高排序，成本相同时按 task_id 排序；每场景前四题为 easy、中四题为 medium、后四题为 hard。这里的难度是该协议下的资源需求分层，不是题目数学复杂度的绝对判断。
5. 题库预算继续使用统一的自选 40,000 token，便于比较规划和节省能力；不会因为某次候选表现好坏事后调整预算。所有 24 题满足成本证据、来源与陷阱核对后，才修改 bank 字段、冻结版本并启动唯一一次验证/考试。届时必须将 token 资源单位与现金价格区分标注。
